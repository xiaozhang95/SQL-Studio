## 一、Agent 模块

### 1.1 结构速览

- 编排：`modules/agent`（上下文压缩、工具白名单、流式编排、SQL 策略、写入确认）。
- 契约：`model/agent`（Message/Event/Conversation/DiscoveryState）。
- 持久化：`agentstate`（`StateDir/agent` 下索引 + 分片记录）。
- 传输：`deepseek/agent`（官方思考 SSE + 工具调用拼装）。
- 装配：`app` 为 Agent 单独创建引擎客户端，元数据/查询复用现有模块，查询预算通过 `query.WithExecutor` 共享。

### 1.2 问题清单

#### A1（P1）会话事件按 delta 全量落盘，每次保存整文件重写，恢复时全量返回

- 证据：流式每个 `reasoning_delta`/`answer_delta` 都追加进 `v.events`，并约每秒把**整条会话**（messages + events）序列化写入新分片、再删旧文件 —— [service.go:87-99](../sql-studio-backend/internal/modules/agent/service.go#L87-L99)、[store.go:158-206](../sql-studio-backend/internal/agentstate/store.go#L158-L206)。
- 上限：单分片 32 MiB，超限后该会话之后每次保存都失败 —— [store.go:18](../sql-studio-backend/internal/agentstate/store.go#L18)。
- 读取：`GET /sessions/{id}` 一次性返回全部事件 —— [persistence.go:79-87](../sql-studio-backend/internal/modules/agent/persistence.go#L79-L87)；前端只能分片解码并主动让出主线程 —— [services/chat:41-53](../sql-studio-frontend/src/agent/services/chat/index.ts#L41-L53)。
- 影响：长回答产生数千个事件（粗估 0.5 MiB/回答）；写入量随会话长度近似 O(n²)；触发 32 MiB 后只在回合结束报一句“本地对话保存失败”；恢复负载随会话线性增长。
- 建议：delta 只在内存聚合，落盘改为最终 `answer`（或按轮压缩后的精简事件）；恢复接口按轮次分页或给出明确的截断策略；保存改为增量/检查点，而不是整条记录重写。

#### A2（P1）容量拒绝发生在用户提问落盘之后，确认等待期间还占着槽位

- 证据：`s.slots` 容量为 2 —— [session.go:57](../sql-studio-backend/internal/modules/agent/session.go#L57)；容量检查在用户事件已追加并保存之后 —— [service.go:100-105](../sql-studio-backend/internal/modules/agent/service.go#L100-L105)；槽位在输入/结果/写入确认（最长 5 分钟）之前获取 —— [service.go:106-113](../sql-studio-backend/internal/modules/agent/service.go#L106-L113)。
- 实测：第三路并发返回“Agent 忙，请稍后重试”时，会话事件里已经留下 `user` + `error` + `turn_end` 三条记录（见第 5 节探针结果）。
- 影响：用户看到一条永远没有回答的提问；两个挂起的确认即可让 Agent 整体不可用；文档只写“与 SQL 窗口共用 4 并发”，没有写这条 2 路上限。
- 建议：先判容量再落盘；槽位只包住模型调用/数据库操作，不包整个回合（尤其不包确认等待）；README 明确 2 路预算。

#### A3（P1）内部错误原样透给界面，用户主动取消被归类成 error

- 证据：预算超时经 `context.Cause` 直接返回，SSE 用 `err.Error()` 发 error 事件 —— [agent_stream.go:77-85](../sql-studio-backend/internal/httpapi/agent_stream.go#L77-L85)；前端再拼前缀 —— [chatEvents:86-91](../sql-studio-frontend/src/agent/utils/chatEvents/index.ts#L86-L91)。
- 实测：界面会显示“本轮未完成：context deadline exceeded”。
- 同类：用户点“取消执行”走 `errWriteCancelled` —— [approval.go:25](../sql-studio-backend/internal/modules/agent/approval.go#L25)，最终以 `error` 收尾，而 `ErrContinueCancelled` 走的是 `stopped`，两者语义不一致。
- 影响：用户看到 Go 内部英文错误；取消和失败难以区分；落盘事件文案（“已停止，本轮未完成。”）与流里发出的文案不是同一套。
- 建议：在 `httpapi` 统一做“错误 → 用户可读文案”映射（超时/取消/用户拒绝/保存失败各一条），并统一取消语义为 `stopped`。

#### A4（P2）上下文压缩请求把 `tools` 序列化成 `null`

- 证据：压缩是唯一走 `Generate` 的路径 —— [context.go:88](../sql-studio-backend/internal/modules/agent/context.go#L88)；请求体 `Tools []model.Tool` 没有 `omitempty` —— [client.go:36-46](../sql-studio-backend/internal/deepseek/agent/client.go#L36-L46)；流式那边加了 `omitempty` —— [stream.go:48-60](../sql-studio-backend/internal/deepseek/agent/stream.go#L48-L60)。
- 影响：OpenAI 兼容接口通常要求 `tools` 是数组，`null` 有被 400 拒绝的风险；而压缩正是最不容易被日常使用触发、也最容易被测试替身掩盖的路径（归档报告也承认压缩只用自动测试验证过，见 [AGENT_ARCHIVE:69](AGENT_ARCHIVE_2026-11-03.md#L69)）。
- 建议：补 `omitempty`，并用真实 Key 跑一次压缩冒烟（外部服务行为本次未验证）。

#### A5（P2）包名与目录大面积不一致，且有两对同名包

- 证据：`modules/agent` 声明 `package chat`、`agentstate` 声明 `package localstate`、`agentlayout` 声明 `package workspace`、`deepseek/agent` 声明 `package deepseek`、`model/agent` 声明 `package model`；`package workspace` 与 `modules/workspace`、`package deepseek` 与 `internal/deepseek` 各重名一次。
- 连锁影响：所有调用点被迫写 import alias（[app/agent.go:9-14](../sql-studio-backend/internal/app/agent.go#L9-L14)），模块 README 标题还写着“Chat业务模块”（[README.md:1](../sql-studio-backend/internal/modules/agent/README.md#L1)），与“每个功能一个包、保留 Go 原生命名”的后端规范相反。
- 建议：统一为 `agent`/`agentstate`/`agentlayout`/`agentstream`/`agentmodel`；至少在迁移前先把 README 与 doc.go 的命名说清楚。

#### A6（P2）同一套 SQL 约束有两份词法扫描

- 证据：`ValidateWriteSQL` 自带一遍 token 扫描，末尾再调 `agentSQLTokens` —— [write.go:17-110](../sql-studio-backend/internal/modules/agent/write.go#L17-L110)、[sqlpolicy.go:20-100](../sql-studio-backend/internal/modules/agent/sqlpolicy.go#L20-L100)。
- 影响：重复实现容易漂移；第二次扫描失败时返回“Agent仅支持单条安全SQL…”这种读语义错误，写入场景下会误导模型和用户。
- 建议：合并为单一扫描器，按“删除禁令 / 多语句 / 未审核函数 / 目标越界”分类报错。

#### A7（P2）文档与界面互相矛盾，前端还展示了一张假的“工具 HTTP 端点表”

- 证据：`API.md` 写“任何模式拒绝…和DDL”，同段下一句又写“支持 CREATE/ALTER”，与 [AGENT.md:43](AGENT.md#L43) 的非删除 DDL 冲突 —— [API.md:113](API.md#L113)。
- 入口名称：README 说“从工作台顶部「Agent」进入” —— [README.md:14](../README.md#L14)，实际 UI 标签是“AI 助手” —— [sectionNavigation:12](../sql-studio-frontend/src/components/sectionNavigation/index.tsx#L12)。
- 假端点表：前端把 Agent 工具显示成 `GET /api/connections`、`POST /api/connections/:id/query` —— [constant/chat:14-21](../sql-studio-frontend/src/agent/pages/chat/constant/chat/index.ts#L14-L21)，实际用在过程卡片上 —— [turnContent:64-65](../sql-studio-frontend/src/agent/pages/chat/components/turnContent/index.tsx#L64-L65)，而后端明确 Agent 是进程内调用、不绕 HTTP（[AGENT.md:16](AGENT.md#L16)）。
- 建议：删掉假端点表或改成“进程内模块调用”，并同步 API/AGENT/README 三处措辞。

#### A8（P2）压缩相关参数彼此不自洽，预算估算与实际工具集不一致

- 证据：摘要提示“最多6000中文字符” —— [context.go:88](../sql-studio-backend/internal/modules/agent/context.go#L88)，但请求 `max_tokens=2400` 且禁用思考 —— [client.go:44](../sql-studio-backend/internal/deepseek/agent/client.go#L44)，接收侧又放宽到 32 KiB —— [context.go:92](../sql-studio-backend/internal/modules/agent/context.go#L92)。

- 建议：统一摘要长度上限（提示、`max_tokens`、接收校验三处一致），估算使用本轮实际 tools，去掉无效形参。

#### A9（P3）服务互斥锁覆盖磁盘 I/O，删除会话用 `context.Background()`

- 证据：[service.go:87-99](../sql-studio-backend/internal/modules/agent/service.go#L87-L99)、[persistence.go:50-62](../sql-studio-backend/internal/modules/agent/persistence.go#L50-L62)、[session.go:133-147](../sql-studio-backend/internal/modules/agent/session.go#L133-L147)。
- 影响：两路并发会话在保存时互相阻塞；磁盘慢时所有会话读写串行化；删除无法被请求取消。
- 建议：序列化交给 `agentstate` 自己的锁，`Service.mu` 只保护内存映射；删除使用请求 context 并加超时。

#### A10（P3）`running → interrupted` 只改内存不落盘

- 证据：[persistence.go:43-46](../sql-studio-backend/internal/modules/agent/persistence.go#L43-L46)。
- 影响：会话被挤出 32 条缓存后重新加载，会再次追加一条 interrupted 事件，事件列表出现重复。
- 建议：状态变更随首次保存持久化，或按 `status`/事件幂等去重。

#### A11（P3）确认 ID 不绑定会话

- 证据：[approval.go:40-50](../sql-studio-backend/internal/modules/agent/approval.go#L40-L50) 只校验 ID 与用途，不校验发起会话。
- 影响：本机单用户风险低（ID 为 48 位随机），但与文档“绑定当前 SQL 和目标”的表述不完全一致。
- 建议：至少把 sessionId 一起纳入校验，代价很小。

#### A12（P3）前后端存在死分支

- `writeConfirmation` 接受 `kind === 'recovery'` —— [writeConfirmation/index.ts:40](../sql-studio-frontend/src/agent/pages/chat/hooks/writeConfirmation/index.ts#L40)，后端从不发送（只发 `input`/`result`/`context`）。
- `Service.Chat` 仅测试使用 —— [service.go:13-15](../sql-studio-backend/internal/modules/agent/service.go#L13-L15)。

### 1.3 Agent 的合理设计（建议保留）

- 写入逐次确认、一次性 ID、服务端绑定 SQL 与目标、前端不能替换 SQL。
- 工具层 + app 适配层双重 SQL 校验，写前重新读取当前引擎。
- 每次数据库操作独立物理连接并即用即释放，会话不持有连接。
- 完整原文与送模上下文分离，摘要失败不覆盖原记录。
- 取消不宣称回滚、恢复不自动重放 SQL。

## 二、能力定位与命名：它到底算不算 Agent

这一节不是缺陷记录，而是对“数据库 Agent”这个名字与实现能力的对齐判断。判据只有一条：**下一步做什么，是模型决定的，还是代码骨架决定的。**

### 2.1 算的部分

- 存在真实的“模型 → 工具 → 观察 → 再决策”闭环：模型可以连续发起工具调用，直到不再调用才输出答案 —— [service.go:126-238](../sql-studio-backend/internal/modules/agent/service.go#L126-L238)。
- 模型确实在自主决定看哪个连接/库、是否追问、查明细还是聚合、失败后怎么改写，不是“一次生成 SQL”的模板调用。
- 这与 SQL 续写/优化那类“把上下文拼进 prompt 让模型吐 SQL”的能力有本质差别。

### 2.2 不算的部分

| 维度 | 现状 | 判定 |
| --- | --- | --- |
| 计划 | 每轮由 harness 追加 `modePrompt` 规定本轮可选动作，工具是固定枚举 | 非自主规划 |
| 重规划 | 仅工具失败时拿到一次 `recovered`，写入失败直接转强制总结 | 一次性、被动 |
| 目标与记忆 | 会话只保存 messages/events/已发现目标/摘要，没有 task/plan/子目标/执行状态 | 无长期意图 |
| 动作空间 | 单语句、≤100 行、禁跨库、函数白名单，删除永久禁止 | 强裁剪 |
| 生命周期 | 每轮 180 秒、断连即取消、只有前台会话 | 不是后台作业 |

证据：`modePrompt` 每轮注入 —— [service.go:142-153](../sql-studio-backend/internal/modules/agent/service.go#L142-L153)；工具固定为 6+1 个 —— [tools.go:226-235](../sql-studio-backend/internal/modules/agent/tools.go#L226-L235)；一次性重规划 —— [service.go:203-212](../sql-studio-backend/internal/modules/agent/service.go#L203-L212)；会话结构里没有任务对象 —— [workspace.go:25-36](../sql-studio-backend/internal/model/agent/workspace.go#L25-L36)；180 秒预算 —— [service.go:106](../sql-studio-backend/internal/modules/agent/service.go#L106)；2 路槽位 —— [session.go:57](../sql-studio-backend/internal/modules/agent/session.go#L57)。

### 2.3 结构性结论：这套权限模型排除了“代理”

- 任何模式都禁止删除类语句（[write.go:95-100](../sql-studio-backend/internal/modules/agent/write.go#L95-L100)），且每次写入都要人工逐次确认、等待最长 5 分钟 —— [approval.go:51-71](../sql-studio-backend/internal/modules/agent/approval.go#L51-L71)。
- 因此它**不可能自主完成一个多步目标**：每一步写入都必须停下来等人。它更准确的定位是“带工具调用的副驾驶（copilot）”，而不是“受限的 agent”。
- 对本地 SQL 客户端，这个取舍是正确的（用户就在屏幕前、写入不可撤销、还有删除红线）；需要修正的是命名，而不是架构。

### 2.4 命名建议

- 对外继续叫“AI 助手 / 数据库助手”（界面本来就是这样 —— [sectionNavigation:12](../sql-studio-frontend/src/components/sectionNavigation/index.tsx#L12)），不用“代理”承诺自主性。
- 文档首次出现时补一句定位：有界工具调用助手（bounded tool-use assistant），不是自主代理。
- `modules/agent` 这类目录名可以保留（改名成本高），但 README/doc.go 要说明它实现的是工具调用闭环，不是自主规划；可与 A5 的包名整理合并处理。

### 2.5 如果确实想往 Agent 方向走

前置条件恰好是本报告里优先级最高的几条：

1. 增加显式目标对象 + 可恢复执行状态（现在连“这轮要做什么”都没落盘），依赖 A1 的事件落盘形态先解决。
2. 批量确认 + 影响面展示（一次确认一组操作），否则人在环每一步，永远只能是副驾驶。
3. 执行后的自我校验（行数/结果不符合预期就换策略），而不是只在报错时重试一次。
4. 长任务后台化 + 完成/失败通知，依赖 A2 的槽位与确认占用先收窄。

## 三、工作区 / SQL 窗口模块

### 3.1 结构速览

- 页面：`pages/workspace` 只组合区域组件，编排集中在 `useWorkspace`，其余按功能拆为 `useDatabaseObjects`、`useDataEditing`、`useObjectManagement`、`useDataExport`、`useQueryHistory`、`useWorkspaceEditor`、`useWorkspacePersistence`。
- 持久化：`WorkspaceStore` 维护轻量索引 + 按 SHA256 内容寻址的 draft/result 分片；后端 `modules/workspace` 校验、`statefile` 落盘并回收孤儿内容。
- 执行：前端用引擎适配器 `splitStatements` 切分，逐条调用单语句接口；失败/取消即停，逐条记历史。

### 3.2 问题清单

#### W1（P1）Ctrl/Command+Enter 是 window 级捕获，在别的界面也会执行当前 SQL

- 证据：监听器挂在 window 捕获阶段并 `stopPropagation` —— [useWorkspace:377-388](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L377-L388)。
- 工作台未卸载：进入 Agent 页只是 `display:none` —— [App.tsx:29-31](../sql-studio-frontend/src/App.tsx#L29-L31)，编辑器与 CodeMirror 实例都还在。
- Agent 输入框只处理 Enter 且不拦截 Ctrl 组合 —— [composer:75-78](../sql-studio-frontend/src/agent/pages/chat/components/composer/index.tsx#L75-L78)。
- 执行入口只检查 `running`/`pageReady`/连接已打开，不检查当前 section 和弹窗 —— [useWorkspace:976-984](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L976-L984)；而查询页执行始终带 `allowWrite: true` —— [useWorkspace:913-917](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L913-L917)。
- 复现：打开一个连接和一个有 SQL 的查询页 → 切到 AI 助手 → 在聊天框按 Ctrl+Enter → 后台执行该 SQL 页；焦点在连接表单 / AI 设置 / 历史搜索里按同样触发。
- 建议：快捷键只在工作台可见且无弹窗时启用，并校验 `event.target` 位于编辑器内；或在 CodeMirror 的 keymap 里处理。

#### W2（P1）“刷新”会把写语句再执行一遍

- 证据：`refreshResult` 直接用当前选中语句重跑 —— [useWorkspace:960-975](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L960-L975)，并以查询页身份执行（`allowWrite: true`）。
- 结果标签只按“有没有返回列”生成 —— [queryOutput:8](../sql-studio-frontend/src/pages/workspace/utils/queryOutput/index.ts#L8)；而 PostgreSQL 的 `INSERT/UPDATE/DELETE ... RETURNING` 返回列且 `isQuery=true`（[API.md:83](API.md#L83)）。
- 影响：在 RETURNING 结果上点“刷新”等于静默再执行一次写入，无任何确认。
- 建议：在 `StatementRun` 上记录语句类别（读/写/DDL），写语句禁用刷新或弹出确认。

#### W3（P1）工作区/历史保存一旦 CAS 冲突就永久失败，只能整页刷新

- 证据：`createLatestWriter` 失败即丢弃队列、不重试 —— [latestWriter:20-30](../sql-studio-frontend/src/utils/latestWriter/index.ts#L20-L30)；`WorkspaceStore.commit` 继续用旧的 `this.doc.revision` —— [services/workspace:134-168](../sql-studio-frontend/src/services/workspace/index.ts#L134-L168)；`userState` 同样只推进 revision，不恢复 —— [userState:27-39](../sql-studio-frontend/src/services/userState/index.ts#L27-L39)。
- 影响：同浏览器两个标签（或残留旧窗口）都会写同一份索引，旧的那个此后每次 409，界面只有右上角“保存失败”小字 —— [saveStatus:6-22](../sql-studio-frontend/src/components/saveStatus/index.tsx#L6-L22)，而草稿仍在内存里继续编辑，属于明确的丢数据路径。
- 建议：409 时重新拉取索引并 rebase（或至少提供“重新载入工作区”的显式出口），并在冲突时暂停/提示继续输入的风险。

#### W4（P2）一个 `running` 同时代表“SQL 在跑”“有弹窗”“某个设计器在存”

- 证据：`running = tabBusy || !pageReady`，`tabBusy` 汇总了运行锁、对象弹窗、分组弹窗、任意设计器 busy —— [useWorkspace:271-272](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L271-L272)、[useWorkspace:144-154](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L144-L154)。
- 表现：树在 `running` 时静默忽略展开/选中/双击 —— [databaseExplorer:352-368](../sql-studio-frontend/src/pages/workspace/components/databaseExplorer/index.tsx#L352-L368)、[395-397](../sql-studio-frontend/src/pages/workspace/components/databaseExplorer/index.tsx#L395-L397)，右键菜单被裁剪成只剩“关闭” —— [databaseExplorer:221](../sql-studio-frontend/src/pages/workspace/components/databaseExplorer/index.tsx#L221)；模型层也有大量静默 `return`（`selectConnection`/`selectObject`/`addTab`/`deleteConnection`/`refreshSchema`）。
- 影响：无关弹窗打开时整个对象树像坏了一样，没有禁用样式也没有提示。
- 建议：拆成 `queryRunning` 与 `uiBlocked`；UI 显式禁用并给原因，而不是让点击落空。

#### W5（P2）执行中切走标签页后，取消入口消失

- 证据：取消按钮只在 `activeRunning` 时渲染 —— [queryEditor:120-124](../sql-studio-frontend/src/pages/workspace/components/queryEditor/index.tsx#L120-L124)、[queryResults:270-274](../sql-studio-frontend/src/pages/workspace/components/queryResults/index.tsx#L270-L274)，而设计上明确允许“运行中切到已有页面”（[useWorkspace/README.md:25](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/README.md#L25)）。
- 影响：切走之后既看不到进度也点不到取消，只能切回去。
- 建议：标签栏给运行中的页持续指示 + 全局取消。

#### W6（P2）长脚本每条语句都整份落盘一次，写入量近似 O(n²)

- 证据：每完成一条就 `publishResult`，而 RunState 携带的是已累计的全部 statements 结果 —— [useWorkspace:940-953](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L940-L953)；每次保存把整个 RunState 作为新分片上传 —— [services/workspace:134-159](../sql-studio-frontend/src/services/workspace/index.ts#L134-L159)。
- 影响：50 条各 1000 行的脚本会写出近似二次方的内容，磁盘上短时间堆积大量分片（24 小时内不会被回收）。
- 建议：批内只更新内存、结束时保存一次；或只增量上传最新一条结果。

#### W7（P2）表数据浏览污染执行历史

- 证据：数据页执行同样 `appendHistory` —— [useWorkspace:939](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L939)；历史按连接仅保留 50 条 —— [queryHistory:4](../sql-studio-frontend/src/pages/workspace/utils/queryHistory/index.ts#L4)；数据页以空 key 挂载历史 hook —— [useWorkspace:101](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L101)、[useQueryHistory:65-71](../sql-studio-frontend/src/pages/workspace/hooks/useQueryHistory/index.ts#L65-L71)。
- 影响：随手点开几张表就会把真正写过的 SQL 挤出 50 条上限；接线方式也难以理解。
- 建议：数据页不计入执行历史，或单独分组展示。

#### W8（P3）`useWorkspace` 是事实上的“总 service”

- 证据：单文件 1176 行、25 个 `useState`、返回 94 个字段 —— [useWorkspace:35](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L35)、[useWorkspace:1076-1174](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L1076-L1174)；其 README 已膨胀成 89 条行为清单 —— [useWorkspace/README.md](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/README.md)。
- 影响：跨功能决策（连接、标签、运行、结果、树、结构、历史、导出、对象管理、设计器）都集中在一处，与“页面只组合、异步状态进入所属 hook”的规范相反，也是 W4/W5/W7 的结构性成因。
- 建议：拆成“查询会话（tabs/runs/results）”“对象树与连接”“布局与持久化”三层，页面做组合根。

#### W9（P3）渲染期 setState 存放派生状态

- 证据：`useMemo` 计算 `reconciledTabs` 后直接 `if (reconciledTabs !== tabs) setTabs(reconciledTabs)` —— [useWorkspace:302-316](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L302-L316)。
- 影响：当前靠引用守卫不会死循环，但这是典型“把派生状态存进 state”，一旦 `reconcileWorkspacePages` 不再稳定就会反复渲染。
- 建议：渲染期直接使用派生结果，或收敛为一次性 effect。

#### W10（P3）interrupted 标记有两套实现

- 证据：[useWorkspace:191-195](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L191-L195) 与 [services/workspace:115](../sql-studio-frontend/src/services/workspace/index.ts#L115)，判定条件与文案不完全一致。
- 建议：收敛到 `WorkspaceStore.hydrate` 一处。

#### W11（P3）清 `runningTabId` 只发生在内存

- 证据：`WorkspaceStore.open` 在内存里改 `doc.index` —— [services/workspace:91-92](../sql-studio-frontend/src/services/workspace/index.ts#L91-L92)。
- 影响：若本次没有后续保存，下次打开仍会把同一页再标记一次 interrupted。
- 建议：打开后安排一次最小提交，或在读取路径直接忽略 stale 的 running 标记。

#### W12（P3）关闭范围后选中项指向已关闭节点

- 证据：[useWorkspace:644-651](../sql-studio-frontend/src/pages/workspace/hooks/useWorkspace/index.tsx#L644-L651) 把 `selected` 设为刚被移出 expanded 的连接/数据库 key。
- 建议：改为选中其父节点或清空选中。

#### W13（P3）MySQL“0 行受影响”被当作失败

- 证据：保存单元格时要求 `affectedRows === 1` —— [useDataEditing:135-136](../sql-studio-frontend/src/pages/workspace/hooks/useDataEditing/index.ts#L135-L136)。
- 影响：把 DECIMAL `1.50` 改成 `1.5`、或大小写不敏感的字符串改成等价值时，MySQL 返回 0，界面报“原值已变化或保存值未产生变更”并中断剩余保存，用户只能放弃重来。
- 建议：非主键列允许 0 行并继续（主键变更仍要求 1），或写前先比较值。

#### W14（P3）孤儿内容回收跑在保存请求路径里

- 证据：`Commit` 成功后在请求内同步执行 `CollectWorkspaceParts` —— [modules/workspace:85-98](../sql-studio-backend/internal/modules/workspace/service.go#L85-L98)；回收会持有 statefile 互斥锁并遍历全部 parts —— [statefile/workspace.go:276-333](../sql-studio-backend/internal/statefile/workspace.go#L276-L333)。
- 影响：分片越多，交互式保存越容易被拖慢，且与其他分区的读写互相阻塞。
- 建议：改为后台 goroutine（自带节流与错误日志），或减少扫描频率。

### 3.3 工作区的合理设计（建议保留）

- 索引与内容分离：索引轻量、内容按 SHA256 寻址、读回校验 hash 与 JSON、临时文件 + rename、严格 CAS。
- 引擎隔离：`splitStatements`/`tableDataSQL`/`updateCellSQL`/`insertRowSQL` 按引擎独立，通用 UI 不拼引号。
- 数据编辑用“主键 + 旧值”做乐观并发，并在保存后重新读取服务端真实值。
- 失败停止后续语句、逐条历史、取消不宣称回滚、恢复不自动执行 SQL。
- 多语句场景下逐条语句的 `USE` 会更新后续语句的默认库，并有测试覆盖。
